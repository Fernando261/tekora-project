# TEKORA — Matriz de garantías SQLite/MySQL (W6.2c-c)

Base inspeccionada: `2441debb728982229d3a8a476ca9618c116b6172`. Complementa el [ADR](ADR-DB-ENGINE-TEKORA.md). Se revisaron las 37 fuentes de migraciones; se detallan las **29–37**, donde se concentra el dominio nativo posterior al catálogo.

**DEMOSTRADO** significa respaldado por restricciones/fuentes y resultados históricos SQLite dentro del alcance sintético de las pruebas citadas, no una certificación nueva de producción ni de cada intercalado posible. **NO DEMOSTRADO** significa sin ejecución equivalente suficiente. **BLOQUEADO** significa impedimento observado (instalación MySQL detenida en 29). En las filas, `S` = SQLite y `M` = MySQL. Todas las ejecuciones de esta matriz están **NOT RUN en W6.2c-c**; no hay código de tests nuevo.

Niveles: **DB** = preservar rechazo de SQL directo mediante restricciones/triggers; **TX** = atomicidad, serialización/CAS e idempotencia bajo competencia; **APP** = autorización/validación de servicios que el esquema no sustituye. Son requisitos acumulativos según la fila. La alternativa MySQL es una hipótesis de diseño para InnoDB, **no una implementación ni equivalencia afirmada**.

Las suites de concurrencia de disponibilidad, reservas, conversaciones y actividad usan dos PDO distintos sobre SQLite en memoria compartida y transacciones solapadas controladas. No son una medición de carga, concurrencia multiproceso sobre disco, WAL o durabilidad tras caída. Esos ensayos y backup operativo siguen **NO DEMOSTRADO**. La recuperación lógica W6.2c-a se limita a otro PDO en memoria. Véase la [propuesta SQLite](../web/w6/W62C-C-SQLITE-NEXT-PR.md).

Para MySQL habrá que probar **cada fila** tanto con SQL directo como por servicios cuando aplique: aislamiento fijado, conexiones independientes, escrituras intercaladas reales, errores/deadlocks y reintentos sin duplicación, transacciones exteriores, restricciones activas y restore. CHECKs MySQL no sustituyen invariantes entre filas.
