# V8.1.8 · Aprovisionamiento MySQL y preparación VPS

Base de revisión: e1cf31c66555a00b7ee7bc1bcd986d0d811f459b. Los procedimientos se revisan con datos sintéticos. La página provisional de tekora.mx permanece activa hasta una autorización de publicación separada.

## Qué instala el comando

`tekora:mysql:provision` instala 39 identidades en orden, con 30 migraciones compartidas y nueve variantes en `database/mysql/migrations/`. El selector rechaza cambios en el número de identidades o variantes sin actualizar explícitamente el plan. Entre las dos rutas, cada identidad se ejecuta una sola vez. Solo se inicializa el catálogo de categorías con el seeder versionado. El seeder general incluye una cuenta de prueba y queda fuera del procedimiento.

El comando usa una conexión Unix propia a `tekora` como `tekora_migrator@localhost`. Verifica MySQL 8.4.13, InnoDB, `utf8mb4_unicode_ci`, modo estricto, UTC, FK, REPEATABLE READ y binlog ROW. Verifica que el reloj SQL siga leyendo tiempo real con `SESSION timestamp` fijado a un año anterior. El reloj B2 conserva `SYSDATE(6)`, la función se declara `NOT DETERMINISTIC` y la retención sigue siendo de 900 segundos. No activar `sysdate-is-now`. Un watermark adelantado bloquea la operación hasta investigar reloj, restauración y trazas.

El bloqueo consultivo protege la instalación frente a otro aprovisionador; durante instalación o restore el administrador debe mantener fuera a otros escritores y a otras herramientas de DDL. MySQL aplica commits implícitos a DDL. La marca `installing` precede a las migraciones. La marca `ready` sella los hashes del plan y de las definiciones. Verificar compara definiciones, orden de triggers, motor, DEFINER, libro, función y watermark. No se ejecutan pasos en una base sellada compatible. Ante esquema parcial, alterado o candidato incompatible, conservar la evidencia y diagnosticar fuera de línea. Para una primera instalación fallida, preparar un esquema nuevo en una instancia independiente y conservar la fallida. Para una instalación con datos, restaurar un respaldo acreditado en otra instancia y reconciliar antes de considerar un cambio. No borrar el esquema fallido como parte de este procedimiento.

Los comandos ordinarios `migrate`, `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `migrate:rollback` y `db:wipe` siguen bloqueados para MySQL. `migrate:status` es solo lectura y necesita autorización de metadatos. El catálogo histórico SQLite conserva su propia ruta.

## Permisos y binlog

| Cuenta local | Alcance | Control |
| --- | --- | --- |
| Administrador MySQL | Crea esquema/cuentas, aplica GRANT, controla la ventana y restaura en un destino aislado | Fuera de Laravel, opción privada para CLI por socket |
| `tekora_migrator` | DDL, lectura y escrituras de instalación en `tekora`, `SHOW_ROUTINE` global para acreditar definiciones | JSON privado, `SET_ANY_DEFINER` solo durante instalación, credencial fuera de releases |
| `tekora_definer` | Cuenta bloqueada. Lee el esquema y ejecuta lógica de rutinas, vistas y triggers. Inserta avisos/eventos y actualiza holds y reloj desde los objetos autorizados | Sin login; SQL SECURITY DEFINER en vistas/rutinas. Acreditar su presencia antes de restaurar |
| `tekora_app` | DML por tabla, ejecución del reloj y lectura de vistas, credenciales de sesión/tokens | Sin DDL, `SUPER`, GRANT, acceso a esquemas ajenos ni cambios globales; restricciones y triggers activos |
| `tekora_backup` | SELECT, SHOW VIEW, TRIGGER y EVENT en `tekora`, SHOW_ROUTINE para dump | Operación exclusiva del administrador. TRIGGER/EVENT conceden capacidades DDL por diseño de MySQL; no entregar esta cuenta a Laravel |

La ventana con binlog ROW habilita temporalmente `log_bin_trust_function_creators` y `SET_ANY_DEFINER` para el migrador. Ejecutarla en un servidor de uso dedicado, con la aplicación detenida, sin otras cuentas no autorizadas con DDL/Routine/Trigger. El script repone OFF y revoca tras éxito, error o señal manejable. Si el host o proceso se interrumpe de forma abrupta, un administrador debe comprobar ambos desde el socket y corregirlos antes de habilitar la aplicación:

```sql
SET GLOBAL log_bin_trust_function_creators=OFF;
SELECT @@global.log_bin_trust_function_creators;
SELECT USER, HOST, PRIV FROM mysql.global_grants
WHERE USER='tekora_migrator' AND HOST='localhost' AND PRIV='SET_ANY_DEFINER';
-- Si permanece la concesión:
REVOKE SET_ANY_DEFINER ON *.* FROM 'tekora_migrator'@'localhost';
```

## Instalación propuesta en Ubuntu 24.04 x86_64

El preflight exige 800 MiB de RAM y 1 GiB nominal de swap. Linux informa en `SwapTotal` los KiB utilizables, sin la primera página que contiene la cabecera. El mínimo utilizable se calcula restando de 1.048.576 KiB una página base, obtenida con `getconf PAGESIZE`. Con páginas de 4 KiB, 1.048.572 KiB cumple y 1.048.571 KiB se rechaza. Si el tamaño de página no se puede determinar, el preflight falla.

1. Mantener cloudflared y las ubicaciones existentes. `tekora.mx` llega por túnel a `127.0.0.1:8083`; conservar `prueba.tekora.mx` en 8082. No abrir 3306, 33060, 8083 ni FPM. Ejecutar `deploy/vps/preflight.sh /srv/tekora` con los directorios creados. El perfil previsto tiene dos CPU, 895 MiB RAM, 1 GiB swap y 2,8 GiB libres de 8,1 GiB; reservar al menos 2 GiB para preparar un release. MySQL sigue con 20 conexiones, buffer de 128 MiB, redo de 100 MiB, binlog 64 MiB/archivo y 259200 s de retención. Vigilar picos y espacio de binlog. Si el build no cabe, compilar Node 22 con el mismo lock en otro host y validar el manifiesto antes de generar el release.
2. Crear `/srv/tekora/releases` y `/srv/tekora/shared/storage/app/{private,public}` con propietario del servicio. Usar usuario de despliegue dedicado y el mismo propietario para Laravel/PHP-FPM o aplicar una ACL explícita de solo lectura a FPM para el entorno y el cache generado. Nginx requiere lectura de `public` y travesía de los padres; no necesita lectura de `.env` ni escritura. Solo FPM/CLI de Tekora escriben `storage` y `bootstrap/cache`. Mantener el socket FPM `/run/php/php8.3-fpm.sock`, ondemand, 3 procesos, `memory_limit=128M`. Separar los logs diarios de Laravel de los de Nginx y systemd.
3. En una instalación nueva y con copia de seguridad si ya existe una aplicación, el administrador ejecuta `umask 077; mysql --defaults-file=/ruta/privada/admin.cnf --protocol=SOCKET --batch < deploy/vps/mysql-accounts.sql > /ruta/privada/cuentas.txt`. Es un script para un destino inicialmente vacío. Usar el cliente 8.4, un `[client]` con usuario y socket, y contraseña solo en archivo protegido si aplica. Extraer las contraseñas generadas directamente a archivos 0600; no copiar su contenido al terminal ni al histórico. El JSON del instalador contiene exactamente las claves `socket` y `password`. Ejecutar `deploy/vps/provision.sh /ruta/privada/admin.cnf /ruta/privada/migrator.json`, aplicar `mysql-runtime-grants.sql` como administrador y verificar con `provision.sh ... --verify`. El usuario PHP que ejecuta el comando debe poseer el JSON. La cuenta de runtime no utiliza admin.cnf ni migrator.json.
4. Copiar `deploy/vps/production.env.example` a `/srv/tekora/shared/production.env` modo 0600. Establecer una APP_KEY nueva generada con `php artisan key:generate --show` redirigida a un archivo 0600 y transferida al entorno de forma segura. Conservarla en las actualizaciones y respaldarla separadamente. Rellenar DB_PASSWORD y SMTP mediante canales privados. No definir `DB_URL` ni credenciales de pago. Mantener host-only para la cookie de sesión, Secure, HttpOnly, SameSite=Lax y CSRF de Laravel habilitado. Configurar un remitente y credenciales SMTP dedicados. Comprobar envío/recuperación con un buzón de prueba antes de publicación; la prueba local con mailer `array` no acredita SMTP en la VPS.
5. Preparar el release sin cambiar `current` ni el sitio público. Con el SHA revisado disponible en el clon existente, ejecutar `deploy/vps/prepare-release.sh /srv/tekora /home/tekoraadmin/tekora-preparacion/web SHA`. Instala Composer desde lock sin dev/scripts, ejecuta `npm ci` y Vite, vincula los discos y genera caches. Config cache contiene credenciales. Antes de activar, verificar propietario y permisos de `.env`, cache y `public/storage`. En el release nuevo, verificar `php artisan route:list --path=api/v1`, bundle en `public/build/manifest.json` y `php artisan about`. Hacer el smoke de Laravel en loopback usando una configuración de candidato temporal que conserve la página provisional, un host HTTP local no accesible desde el túnel y el mismo FPM. Probar catálogo, login, recuperación de correo, CSRF, login Bearer y flujo comercial con cuentas sintéticas. Verificar que las rutas de checkout de prueba devuelvan 404. Retirar la configuración temporal terminada la revisión.
6. Solo tras aprobar el smoke, respaldo y revisión humana, usar `deploy/vps/switch-release.sh /srv/tekora SHA --approved`. Validar la configuración candidata con `nginx -t`, conservar copia de la configuración provisional y recargar Nginx únicamente al momento de publicar. `tekora.nginx.conf` limita el origen al loopback con host fijo, permite FastCGI solo en `/index.php` y sirve `public`. Ante el tramo HTTP local, Nginx establece `HTTPS=on` en FastCGI. Laravel no necesita confiar en proxies ni en cadenas Forwarded enviadas por el cliente. La tasa por IP desde el túnel agrupa visitantes hasta habilitar y verificar una política de IP autenticada. Revisar este efecto antes de una apertura con tráfico real. Comprobar el origen con `curl -fsS -H 'Host: tekora.mx' http://127.0.0.1:8083/_tekora/origin-health`. Después comprobar HTTPS público, sesión, recuperación, rutas API, acceso a fotos autorizadas y rechazo de archivos privados. CORS de producción no autoriza otros orígenes web; la app nativa Bearer no depende de CORS.
7. Si el smoke posterior falla, volver a la configuración provisional o al enlace del release previo con `switch-release.sh`; recargar FPM de forma ordenada para evitar caches antiguas. Revertir código solo a un release compatible con el esquema actual. La recuperación del esquema/datos se decide por separado y nunca se ejecuta por rollback de código.

Para esta demo `QUEUE_CONNECTION=sync` limita procesos. La tarea de envío de códigos de identidad usa Laravel Queue y se ejecuta en el request. El repositorio actual no programa tareas en `routes/console.php`. Si las métricas justifican colas asíncronas, cambiar de forma explícita a `database` y añadir un único worker systemd de usuario de servicio con `queue:work --sleep=3 --tries=3 --timeout=45` y `retry_after` mayor que el timeout; reiniciarlo en cada release. Programar `schedule:run` bajo el usuario de servicio solo cuando exista una tarea revisada. Rotar logs Nginx con logrotate y Laravel con el driver daily de siete días.

## Respaldo y recuperación ensayable

- Detener escritores web, móviles y workers y bloquear DDL durante el respaldo conjunto de BD y almacenamiento. Usar el archivo privado de cliente 8.4 como `tekora_backup`. Ejecutar `deploy/vps/backup.sh /ruta/privada/backup.cnf /srv/tekora/shared/storage /destino-privado/nuevo`. Es un dump de snapshot InnoDB con rutinas, triggers, vistas y eventos, más `storage/app/private` y `storage/app/public`. `SHA256SUMS` aparece solo si terminaron las dos copias. No usar los checksums como autenticación de orígenes desconocidos. Conservar cifrado fuera del host, con una copia local reciente si hay espacio, siete diarias externas y cuatro semanales según capacidad. Conservar aparte APP_KEY, manifiesto de release y configuración segura. No automatizar eliminaciones sin acreditar la copia y retención.
- Preparar otra instancia MySQL 8.4.13 aislada y por socket, con esquema `tekora` vacío y cuentas nuevas. Ejecutar `deploy/vps/restore.sh admin-destino.cnf /ruta/respaldo /ruta/almacenamiento-nuevo migrator-destino.json --isolated-empty-target`. Verifica hashes y rutas del archivo antes de extraer, rechaza un destino con objetos, comprueba DEFINER bloqueado, sello, 39 migraciones, watermark y cada FK mediante anti-joins. Una restauración incompleta queda para diagnóstico. Mantener el origen fuera del restore y comparar muestras de identificadores, estado y fotos antes de cualquier uso.
- Los datos sintéticos del laboratorio y los archivos restaurados se descartan al terminar. El artefacto CI conserva JUnit/logs, no dump ni archivos privados. La copia lógica acredita restauración al punto del respaldo. Recuperación a un punto en el tiempo mediante binlog requiere un procedimiento y ensayo adicional; los tres días de binlog no sustituyen una copia externa.
