# M3.1 — Checkout sintético por API móvil (exclusivamente local)

Este incremento **no implementa cobros reales**, no agrega migraciones y no modifica la SQLite normal. Reutiliza el almacenamiento y el predicado B3.2 de la web mediante Sanctum y una verificación adicional de cliente propietario.

## Límite de seguridad

Las operaciones GET y POST de `/api/v1/reservations/{reservation}/demo-checkout` devuelven 404 a menos que se cumplan TODAS estas condiciones: entorno local/testing, sin configuración cacheada; host e IP de petición en loopback; conexión SQLite situada en una carpeta temporal `tekora-b32-*` con marcador `.tekora-b32-synthetic`; tabla `synthetic_checkout_attempts` ya generada por el exportador. Este endpoint **no funciona** sobre `C:\xampp\htdocs\TEKORA\database\database.sqlite`. No reproducir marcadores ni migrar tablas sintéticas hacia bases existentes.

## Operaciones

- GET: estado del método de prueba de una reserva propia. Devuelve `data` con `reservation_id`, `method`, `status`, `reference`, `can_choose`, `can_confirm`, `amount`, `server_now`, `expires_at`, `remaining_seconds`, `synthetic_only=true`. Nunca devuelve número de tarjeta, CVV, token, correo ni clave de idempotencia.
- POST para efectivo: `{"method":"cash","idempotency_key":"UUID"}`.
- POST para tarjeta ficticia: `{"method":"card","card_number":"4242424242424242","expiry":"12/30","cvv":"123","idempotency_key":"UUID"}`. Las otras dos tarjetas permitidas del B3.2 simulan rechazo y fallo temporal. No introducir tarjetas reales.
- Requisitos: solicitud y cotización aceptadas, horario retenido y plazo vigente. POST reusa `LocalCheckoutAttemptStore::submit` y la confirmación B2 sigue aplicando `LocalCheckoutAttemptStore::permitsCommit`.
- Un resultado `test_approved` es **ficticio**. `awaiting_cash` habilita confirmar horario pero NO indica efectivo recibido. Ambos mantienen `payments.enabled=false` y `future_payment.enabled=false`.

## Ejecución controlada Windows

1. Desde un clon **aislado sin .env**, seguir `docs/payments/B3.2-INTEGRATED-LOCAL.md` para generar una base efímera y lanzar el servidor en `127.0.0.1:8097`.
2. En Expo Web, en la misma PC: `EXPO_PUBLIC_API_BASE_URL=http://127.0.0.1:8097/api/v1` y `EXPO_PUBLIC_ALLOW_LOCAL_HTTP=1` en desarrollo.
3. Autenticarse con el cliente **temporal** que entrega el lanzador, no con los usuarios de la SQLite normal.
4. El hold inicial dura 900 s; al caducar generar otra fixture, nunca modificar el reloj, marcadores ni estado.
5. Comprobar tarjeta aprobada, rechazada, efectivo, autorización ajena, vencimiento, idempotencia y actualización de la reserva en móvil.
