# B3.0 — Contrato comercial compartido

Solo preparación comercial; no pagos, ni siquiera sandbox. La confirmación B2 vigente no cambia. `/demo/checkout` sigue siendo HTML local/testing aislado y no se reutiliza como API.

## Endpoints

Base móvil `/api/v1`, Bearer Sanctum real de cliente; se revalidan rol, permisos y propiedad actuales, también en cuentas duales. No basta una cookie web ni un token con otro nombre/ability. Respuestas `data` o `error:{code,message,fields}`, `no-store, private`, JSON y `nosniff`. IDs ajenos e inexistentes: 404 antes de validar cuerpos. Escrituras de cotización: 10/minuto por cliente, 40/IP, además del límite privado común.

| Método | Ruta móvil | Propósito |
| --- | --- | --- |
| GET | `/inquiries/{inquiry}/quotes?page=1&per_page=12` | Historia propia, orden `issued_at DESC, id DESC`; máximo 50/página |
| POST | `/inquiries/{inquiry}/quotes` | Emitir/recuperar con `idempotency_key` UUID; respuesta 200 tanto nueva como repetida |
| GET | `/quotes/{quote}` | Snapshot monetario, vigencia y aceptación |
| POST | `/quotes/{quote}/accept` | Consentimiento explícito `acknowledge:true`; idempotencia por quote_id |
| GET | `/quotes/{quote}/acceptance` | Estado posterior y hora del servidor |
| GET | `/reservations/{reservation}/checkout-context` | Contexto comercial informativo; no inicia pagos |

Web: `GET /cuenta/reservas/{reservation}/contexto-comercial`, sesión `auth:web`, mismo `CheckoutContext` y mismo recurso JSON. Es un endpoint JSON privado de consulta, no la página de demo. No acepta parámetros ni cuerpos adicionales y no requiere ejecutar migraciones.

Listado/detalle/estado usan un modelo de lectura sobre la historia existente y `PricingStore`; emisión y aceptación ejecutan `SyntheticQuotes`. El consentimiento usa las mismas reglas `accepted` de la web. No se admite importe, comisión, participantes, estados financieros o vencimiento enviados por el cliente. La emisión conserva el precio original al repetir una clave y devuelve 409 si la clave pertenece a otra solicitud del mismo cliente. La aceptación requiere consentimiento en cada intento; una ya persistida sigue aceptada después del vencimiento de su ventana inicial. Aceptar no reserva horario ni cobra.

`Service.price` es una ampliación aditiva del catálogo: precio publicado informativo o `null` si no existe; nunca un cero inventado. El cliente debe presentar la cotización antes de aceptar, porque el precio publicado puede cambiar. Los snapshots usan centavos enteros, el redondeo existente y comisión del 15 % incluida; no sumar otra vez la comisión. No se exponen claves de idempotencia, emails o datos bancarios.

## Secuencia para el desarrollador móvil

Ejemplos completos, schemas y errores: `openapi.json`, operaciones `listInquiryQuotes`, `issueInquiryQuote`, `getQuote`, `acceptQuote`, `getQuoteAcceptance`, `getCheckoutContext`; ejemplos `B3QuotePending`, `B3QuoteAccepted`, `B3QuoteAcceptance`, `B3Quotes`, `B3CheckoutContext`.

```http
POST /api/v1/inquiries/93/quotes
Authorization: Bearer <token-local-sintetico>
Content-Type: application/json

{"idempotency_key":"b54d8c80-3dad-42c2-9238-ae030bd56290"}
```

Obtener `data.id`, mostrar `data.amount` y fechas; no aceptar automáticamente. Después de una acción consciente del usuario:

```http
POST /api/v1/quotes/161f9f2b-6479-49de-9f68-aa01c78ab7bb/accept
Authorization: Bearer <token-local-sintetico>
Content-Type: application/json

{"acknowledge":true}
```

Respuesta 200 con el mismo snapshot, `acceptance.state="accepted"` y `accepted_at`. Consultar el estado mediante GET; si se perdió una respuesta de escritura, consultar historia y repetir la misma intención, nunca generar una clave nueva para ocultar incertidumbre.

A continuación: GET de opciones privadas, propuesta con `quote_id` explícito por el endpoint de reservas existente, aceptación del prestador por la web vigente, GET del contexto y confirmación final del cliente por PATCH `/reservations/{reservation}/commit`. Esa confirmación sigue sin exigir pagos en B3.0. No se implementa API de prestador en este incremento.

## Interpretación del contexto

El título del servicio se toma del snapshot de la solicitud, como en la cotización web; no se sustituye por una edición posterior del catálogo.

El ejemplo completo `B3CheckoutContext` muestra total 100000 centavos, comisión incluida 15000 y prestador 85000. `server_now` y las fechas son UTC. La retención dura exactamente 900 segundos desde la aceptación del prestador; no desde emitir o aceptar una cotización.

- Captura una lectura coherente y un reloj observado común, incluido el high-water B2. No llama a la reconciliación de expiraciones ni modifica filas de reservas/retenciones. El bookkeeping de autenticación Sanctum permanece vigente.
- `hold.state` deriva la expiración al observarla; `stored_state` permite distinguir historia aún no reconciliada. En el límite exacto, remaining_seconds=0 y elegibilidad=false. No se extiende ni reactiva una retención. El contador móvil es orientativo, no autoridad.
- Una cotización aceptada conserva su aceptación aunque expire su ventana inicial. Un hold vivo congela el horario: modificaciones posteriores de precio, disponibilidad o publicación no lo desplazan, conforme a B2.
- Sin cotización comercial: quote/amount nulos y pago no elegible. No se inventan intentos, autorizaciones, recibos ni importes cero.
- `commercial_eligible` es un preflight informativo, sin garantía de admisión. `enabled=false`, `can_start=false` y `payments_not_enabled` son incondicionales. No hay configuración de cliente que active pagos. La confirmación actual usa su workflow y sus guardas existentes, no este booleano.
- Reserva no pendiente, solicitud no aceptada, participantes sin permiso, falta de hold, hold terminado o servicio comenzado bloquean la elegibilidad. Inconsistencia de vínculos/snapshot/reloj o error de almacenamiento: 503 sin contexto; nunca tratarlo como elegible.

## Matriz cliente web / API

No se declara paridad global terminada. Se cierran los faltantes comerciales de B3.0; los restantes requieren incrementos propios.

| Funcionalidad cliente web | Equivalente `/api/v1` | Estado / alcance |
| --- | --- | --- |
| Inicio/cierre de sesión | `/auth/login`, `/auth/logout`, `/me` | Existente, Sanctum; sesión web y token son transportes distintos |
| Registro y recuperación de contraseña | Sin equivalente móvil | Pendiente fuera de B3.0 |
| Perfil propio, nombre/foto, identidad/roles | `/me` solo consulta parcial | Pendiente escritura/perfil completo; no elevar roles mediante token |
| Panel cliente | Solicitudes/conversaciones/reservas y `/me` | Parcial: composición disponible; agregados del panel sin endpoint específico |
| Catálogo/búsqueda/detalle | `/services`, `/services/{service}` | Existente; B3 añade precio estructurado informativo |
| Prestadores/perfil público | `/providers`, `/providers/{provider}` | Existente; reseñas públicas no están proyectadas como en la web |
| Disponibilidad | `/services/{service}/availability` | Existente, mismo horario civil |
| Solicitar, listar, consultar y cancelar solicitud | `/services/{service}/inquiries`, `/inquiries`, `/inquiries/{inquiry}`, `/cancel` | Existente, mismos workflows |
| Conversaciones, enviar/consultar mensajes y marcar leídos | `/conversations`, `/inquiries/{inquiry}/messages`, `/messages/read` | Existente, idempotencia y cursor propios |
| Listar, emitir, consultar y aceptar cotizaciones | Nuevas rutas de cotización | Cerrado en B3.0; solo cliente propietario |
| Precio, comisión, vigencia y aceptación posterior | Catálogo `price`, cotización `amount`, `/acceptance` | Cerrado en B3.0, sin recalcular importes en controladores |
| Opciones/propuesta/listado/detalle/cancelación de reservas | `/inquiries/{inquiry}/reservation-options`, `/reservations`, `/reservations/{reservation}`, `/cancel` | Existente; propuesta usa quote_id aceptada explícita |
| Confirmación final del cliente en B2 | `/reservations/{reservation}/commit` | Existente, sin cambiar exigencia de pago |
| Contexto comercial de reserva | `/reservations/{reservation}/checkout-context` | Nuevo, compartido con endpoint web JSON |
| Crear/consultar/retirar reseña propia | Sin API de reseñas | Pendiente fuera de B3.0; no eludir finalización real del servicio |
| Notificaciones y marcado de lectura | Sin API de notificaciones | Pendiente fuera de B3.0; unread de conversaciones no las sustituye |
| Activar/gestionar rol prestador, publicar servicios y decidir como prestador | API móvil actual solo cliente | Fuera de alcance; no fingir capacidad móvil de prestador |
| Demo HTML de checkout | No corresponde como operación comercial | Aislada; futura pantalla nativa consumirá el contrato comercial, no HTML |
| Cobro, tarjeta/3DS, reembolsos y liquidación | No existen endpoints ejecutables | Diseño B3.1 solamente; nunca simularlos como efectuados |

No se modifican las 39 migraciones, las dependencias, la demo ni los comandos de reservas/B2. Los únicos ajustes de modelos B2 permiten pasar un instante observado a sus proyecciones de lectura; los llamadores existentes mantienen el comportamiento por defecto.

Las regresiones históricas conservan las 22 rutas API originales mediante un fingerprint de métodos, URIs, acciones, middleware y restricciones obtenido del Git base autorizado; solo admiten las seis operaciones B3.0 declaradas. Las allowlists públicas añaden únicamente price y comprueban null en servicios legacy. No se eliminan escenarios ni oráculos de seguridad.
