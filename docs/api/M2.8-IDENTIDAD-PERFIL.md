# M2.8 · Identidad y perfil del solicitante

El backend utiliza la cuenta central de Tekora. `POST /auth/login`, `GET /me` y `POST /auth/logout` conservan sus contratos. Las rutas de esta guía son relativas a `/api/v1`. Usa HTTPS en el entorno autorizado y guarda el token Sanctum en el almacenamiento seguro del dispositivo.

| Método y ruta | Entrada | Resultado |
|---|---|---|
| `POST /auth/register` | JSON con `email` | `202` neutral. Envía al correo un código de registro de 30 minutos. |
| `POST /auth/register/confirm` | JSON con `email`, `token`, `name`, `age`, `gender`, `password`, `password_confirmation` | `202`. Un código válido crea un solicitante si no existe la cuenta. El mismo intento puede repetirse sin reemplazar una cuenta. Iniciar sesión por separado. |
| `POST /auth/forgot-password` | JSON con `email` | `202` neutral. La entrega del código depende de que exista una cuenta de solicitante elegible. |
| `POST /auth/reset-password` | JSON con `email`, `token`, `password`, `password_confirmation` | `200`. Consume el código, cambia la contraseña central y revoca los tokens Sanctum. La app debe limpiar su token y volver a iniciar sesión. |
| `GET /me/profile` | `Authorization: Bearer …` | `200`. `id`, `name`, `email`, `age`, `gender`, `email_verified` y `photo_url`. |
| `PATCH /me/profile` | Bearer y JSON con `name` | `200` con el perfil actualizado. Repetir el mismo nombre conserva el valor. |
| `POST /me/photo` | Bearer y `multipart/form-data`, parte `photo` | `200` con el perfil. JPEG, PNG o WebP, hasta 2 MiB. Al perder la respuesta, consulta el perfil antes de volver a subir el archivo. |
| `GET /me/photo` | Bearer | `200` con bytes de imagen o `404` si no existe una foto compatible. |

Presenta el código como texto opaco. Ofrece el pegado del sistema y desactiva autocorrección, autocapitalización y teclado numérico. Con AES-256-CBC medimos 340 caracteres para un correo sintético de 24 bytes, 512 para uno de 112 bytes y 768 para uno de 253 bytes. La longitud varía con el correo y el mensaje cifrado. Teclear el código resulta poco práctico. Para una iteración del cliente, un Android App Link HTTPS verificado puede abrir la pantalla con la prueba opaca en el fragmento. Conserva el pegado como respaldo y excluye el valor de la telemetría, los logs y la cadena de consulta. El servidor debe seguir verificando el correo, la autenticidad y la caducidad del mismo código antes de registrar.

En los flujos nuevos el correo es ASCII y se normaliza a minúsculas. En cuentas recién registradas usa ese correo normalizado para iniciar sesión. `age` admite 1 a 255. La contraseña tiene un mínimo de 8 caracteres y un máximo de 72 bytes UTF-8 y requiere confirmación. Envía cuerpos con las claves indicadas y deja vacía la consulta de las escrituras. Si una cuenta existente intenta registrarse, el nombre, el rol y la contraseña quedan intactos.

La recuperación usa el broker central de Laravel con su vencimiento configurado, 60 minutos de forma predeterminada. Los códigos vencidos, usados o incorrectos devuelven el mismo `422`. El cambio de contraseña bloquea la cuenta durante la comprobación y el consumo del código, y rota el token de recordar sesión. Las sesiones web activas siguen bajo la política de sesión existente.

El perfil de una cuenta dual corresponde al mismo usuario central. `photo_url` es `null` o una ruta relativa al origen, como `/api/v1/me/photo`. Envía Bearer al obtenerla. La API omite las referencias históricas externas, incompatibles o que resuelven a otra ruta mediante un enlace simbólico. La política de publicación de fotos que ya usa la web queda bajo el almacenamiento central existente.

## Respuestas que debe manejar el cliente

```json
{"data":{"message":"Si corresponde, recibirás un correo para continuar."}}
```

```json
{"error":{"code":"validation_failed","message":"Los datos enviados no son válidos.","fields":{"token":["El código no es válido o ha vencido."]}}}
```

`401` significa que falta un token válido y `403` que la cuenta o el token no satisface el acceso móvil de solicitante. Usa `error.fields` en `422`. Ante `429`, espera el tiempo definido por `Retry-After`. La solicitud de código tiene un máximo de 3 por 10 minutos por correo y 12 por IP para cada operación. La confirmación tiene 5 por minuto por correo y 20 por IP. El perfil aplica el límite privado general y el límite adicional de 10 escrituras por minuto por actor y 40 por IP. Ante `503` conserva el estado de la pantalla, reconsulta si es una escritura incierta y vuelve a intentar cuando el servicio esté disponible.

## Entrega de correos y verificación

Los flujos con correo requieren un transporte de entrega directo, por ejemplo SMTP, y un trabajador de cola cuando se usa una conexión asíncrona. La dirección viaja cifrada en la cola. Para `sync` la entrega se difiere hasta después de responder. El estado `202` admite retraso o fallo de entrega. Los transportes efectivos `log`, compuestos y `array` fuera de pruebas devuelven `503`, incluso si se resuelven mediante `MAIL_URL`. Las pruebas con datos sintéticos verifican el transporte efectivo y el flujo de códigos dentro de Laravel. En un entorno autorizado queda por probar la entrega SMTP real con su trabajador de cola, el pegado completo desde el correo en Android y la visualización de la foto desde una petición con Bearer.

Para reproducir en un clon independiente con dependencias de los archivos lock y sin `.env`, compila los recursos y ejecuta PHPUnit. `tests/bootstrap.php` fuerza SQLite `:memory:`, sesiones y correo sintéticos. La prueba concurrente utiliza dos conexiones a SQLite de memoria compartida y comprueba que ambas rutas están vacías en `PRAGMA database_list`.

```bash
npm ci
npm run build
php vendor/bin/phpunit --do-not-cache-result tests/Feature/MobileIdentityProfileTest.php tests/Feature/MobileApiAuthTest.php tests/Feature/TekoraW5Test.php tests/Feature/ProfilePhotoIntegrityTest.php
php vendor/bin/phpunit --do-not-cache-result
git diff --check
```
