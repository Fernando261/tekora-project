# M2.0 — Entrega de contrato para la aplicación móvil de Tekora

**Estado:** incremento de documentación y protección de contrato en rama independiente, construido sobre `main` después del PR #48 (B3.2). **No implementa APIs de pago nuevas ni habilita cobros**. La aplicación móvil está fuera de este repositorio; no afirmar que se probó un cliente nativo.

## Decisión arquitectónica

La aplicación móvil **consume los servicios compartidos del backend**, no replica la lógica de negocio de Laravel ni reutiliza HTML como API. La web B3.2 es un **laboratorio privado exclusivamente local**, con tarjetas y efectivo ficticios en una SQLite desechable. La API actual es un contrato de cliente basado en Sanctum y **no tiene escritura de pago**, ni API móvil de prestador. No exponer la SQLite sintética de B3.2 a redes externas ni conectar una app móvil a su servidor de loopback.

**Advertencia de compatibilidad:** el comando B2 `PATCH /api/v1/reservations/{reservation}/commit` normalmente no requiere pago real; sin embargo, **en la fixture web B3.2** el servidor exige un método ficticio antes de confirmar. Por eso una app móvil no puede completar end-to-end ese laboratorio con los endpoints actuales. Los campos `payments.enabled=false`, `future_payment.enabled=false` y `next_action.mobile_execution_available` describen los contratos generales; ninguno autoriza eludir la regla local de B3.2. Esta brecha es un pendiente de implementación futuro, no un endpoint oculto.

## Base de API, autenticación y transporte

- Prefijo `/api/v1`. Token Bearer emitido por Laravel Sanctum obtenido mediante `POST /api/v1/auth/login`; no usar cookie `auth:web` ni un token del navegador como autenticación móvil. `MobileClient` exige rol y permisos de cliente vigentes además de token de nombre con prefijo `mobile:` y ability `client:read`.
- Encabezados: `Authorization: Bearer <token>` y `Accept: application/json`; en comandos con cuerpo, `Content-Type: application/json`. Respuestas privadas `Cache-Control: no-store, private` y `X-Content-Type-Options: nosniff`.
- Errores: `{"error":{"code":"conflict","message":"...","fields":{}}}` (o su variante según estado), sin asumir que una excepción tiene cuerpo `data`. 401 sin Bearer válido o con token vencido; 403 con token de nombre/ability o rol/permisos incorrectos; 404 para recurso inexistente o ajeno; 409 por estado, versión o retención; 422 por datos extra o inválidos; 429 por límite; 503 cuando no es segura la lectura/escritura.
- **Conectividad:** `127.0.0.1` en el teléfono apunta al propio teléfono, no a la PC Windows. No publicar el servidor B3.2 al LAN ni Internet, abrir puertos en Docker o compartir `.env`/credenciales para “hacer que funcione”. La conexión con el dispositivo real requerirá **otro entorno de desarrollo expresamente aprobado**, HTTPS y controles de acceso, sin reutilizar las fixtures efímeras.

## Recorrido nativo que YA está soportado por la API existente

| Momento | Operación móvil | Respuesta/decisión nativa |
| --- | --- | --- |
| Identidad | `POST /auth/login`, `GET /me` | Guardar token en almacenamiento seguro del sistema; cerrar sesión con `POST /auth/logout` |
| Solicitud del cliente | `GET /inquiries`, `GET /inquiries/{inquiry}` | Consultar estado y participantes sin inventar estados |
| Cotización | `GET /inquiries/{inquiry}/quotes`, `GET /quotes/{quote}` | Mostrar monto en centavos/MXN, versión y vencimiento de aceptación |
| Nueva cotización | `POST /inquiries/{inquiry}/quotes` | Enviar solo UUID `idempotency_key` estable; no enviar precio ni comisión |
| Aceptación expresa | `POST /quotes/{quote}/accept` | Enviar `{"acknowledge":true}` después de la acción del cliente |
| Propuesta de horario | `GET /inquiries/{inquiry}/reservation-options`, `POST /inquiries/{inquiry}/reservations` | Conservar `availability_revision`, horario local y `quote_id` aceptada; el servidor verifica disponibilidad |
| Espera del prestador | `GET /inquiries/{inquiry}/journey`, `GET /reservations/{reservation}` | Solo lectura; la aceptación del prestador aún se hace por web |
| Retención comercial | `GET /reservations/{reservation}/checkout-context` | Mostrar snapshot del total, desglose, `server_now`, `expires_at` y `remaining_seconds`; **no iniciar pago** |
| Confirmación B2 | `PATCH /reservations/{reservation}/commit` | En entornos B2 normales, enviar versión e idempotencia; es la **confirmación del horario**, no un cargo. **No ejecutarlo en la fixture B3.2 local sin completar antes su requisito sintético de la web** |
| Cancelación | `PATCH /reservations/{reservation}/cancel` | Enviar `version` actual; en `quoted-slot-hold-v1` enviar también UUID `idempotency_key` estable. Reconsultar estado tras 409 |
| Conversación | `GET /inquiries/{inquiry}/messages`, `POST /inquiries/{inquiry}/messages` | Enviar con idempotencia, no confundir lectura de mensajes con confirmación de reserva |
| Notificaciones | `GET /notifications`, `GET /notifications/unread-count` | Seguimiento existente M1; no equivale a aprobación de pago |

Detalles oficiales de campos y respuestas: `docs/api/openapi.json`, `docs/api/B3.0-COMMERCIAL.md` y `docs/api/UX-C1-MOBILE-JOURNEY.md`. Archivo de peticiones sin credenciales para el colaborador: `docs/api/examples/M2.0-mobile-handoff.http`. La tabla presenta operaciones ya implementadas y **no representa una prueba de la app nativa**.

Los valores `REEMPLAZAR_*` del archivo `.http` son marcadores deliberadamente no ejecutables: sustituirlos solo en una copia local. Obtener fecha/hora y revisión de las opciones actuales; obtener la versión de la reserva después de la aceptación del prestador. Las claves de propuesta y confirmación son UUID distintos y se conservan al reintentar cada intención. El archivo no automatiza la espera del prestador ni acredita un recorrido nativo completo.

## Modelo de interfaz móvil recomendado (sin lógica comercial duplicada)

1. **Acuerdo:** mostrar `commercial.agreed_amount` o `quote.amount`; si es `null`, presentar “Sin cotización aceptada”, nunca `$0`. El total incluye comisión Tekora 15 %, con `commission_basis_points=1500`. No sumarla al total de nuevo.
2. **Horario:** mostrar horas civiles y zona IANA del servicio; instantes del servidor en UTC. El contador visual nace de `server_now` y `expires_at`, pero la admisión la decide siempre Laravel. La retención es de **900 segundos exactos** y jamás se renueva recargando la pantalla.
3. **Acción:** `GET /inquiries/{inquiry}/journey` da `next_action.code` y `reference` tipada. No interpretar textos como comandos ni construir una URL de pago a partir de ellos; validar que el endpoint correspondiente existe y que `mobile_execution_available` autoriza esa UI. Ninguna bandera de lectura sustituye permisos o validación de la escritura.
4. **Confirmación:** para `quoted-slot-hold-v1` enviar `version` e `idempotency_key` UUID estable; usar la versión de la **reserva** (`data.version` en su detalle o `data.reservation.version` en checkout-context), no `hold.version`. Después de la aceptación web del prestador, volver a consultar esa versión antes de confirmar. Si se pierde la respuesta, reconsultar la reserva antes de reintentar **la misma intención**, sin claves nuevas para ocultar un resultado incierto. Ante 409, refrescar snapshot; no aumentar el reloj ni forzar estado local `confirmed`.
5. **Pagos:** si `future_payment.enabled=false` o `payments.enabled=false`, mostrar un estado informativo (“Pago móvil no disponible”) y **no renderizar campos de tarjeta ni simular cobros**. `commercial_eligible=true` es solo preflight informativo, no permiso para cobrar.
6. **Estado final:** la reserva solo está confirmada cuando el servidor responde `confirmed`. Los estados `test_approved` o `cash_received` de B3.2 pertenecen a la fixture web y **no son comprobantes bancarios ni endpoints públicos**.

### Ejemplos de llamadas sin secretos

```http
GET /api/v1/inquiries/42/journey HTTP/1.1
Accept: application/json
Authorization: Bearer <token-movil-del-cliente>
```

```http
GET /api/v1/reservations/17/checkout-context HTTP/1.1
Accept: application/json
Authorization: Bearer <token-movil-del-cliente>
```

El recurso tiene `data.reservation.version`, `data.amount` (puede ser null), `data.hold` (puede ser null), `data.server_now` y `data.future_payment.enabled=false`. Ejemplo **parcial y exclusivamente ilustrativo**:

```json
{
  "data": {
    "reservation": {"id": 17, "status": "held", "version": 1},
    "hold": {"state": "held", "hold_seconds": 900, "remaining_seconds": 450},
    "amount": {"currency": "MXN", "total_cents": 100000, "commission_cents": 15000, "provider_cents": 85000},
    "future_payment": {
      "enabled": false,
      "can_start": false,
      "advisory_only": true,
      "commercial_eligible": true,
      "blocking_reasons": ["payments_not_enabled"]
    }
  }
}
```

Los objetos anteriores están **recortados**; no deben validarse contra el esquema completo como si fueran una respuesta íntegra.

## Matriz de paridad y decisiones siguientes

| Capacidad | Disponible hoy | Próximo trabajo |
| --- | --- | --- |
| Lectura de cotizaciones, importes, retenciones | Sí, API de cliente B3.0/B2 | Integrar pantallas nativas contra OpenAPI |
| Confirmación de reserva B2 normal | Sí, comando existente | Probar en entorno seguro separado del checkout B3.2 |
| Tarjeta ficticia y efectivo B3.2 | **Solo web local** | Diseñar M2.1 con autorización y pruebas separadas; **no publicar escrituras en API de producción** |
| Recepción de efectivo del prestador | Solo web local | Definir autenticación/roles de prestador móvil antes de habilitar comandos |
| Pagos bancarios, 3DS, liquidaciones | **No** | Trabajo posterior con procesador autorizado; fuera de M2.0 |
| Cliente móvil real | No probado aquí | Colaborador implementa y prueba contra entorno de desarrollo aprobado |

## Criterios de aceptación de M2.0

- [ ] Ejecutar `php vendor/bin/phpunit --filter MobileCheckoutHandoffContractTest` en entorno aislado, con evidencia y sin una base comercial.
- [ ] Ejecutar suite completa y build en el entorno autorizado antes de solicitar merge; la versión base B3.2 **no** valida automáticamente estos archivos nuevos.
- [ ] Verificar que no se agregaron rutas de pago de escritura, tablas/migraciones financieras, credenciales, hosts públicos ni puertos.
- [ ] Revisar con el desarrollador de la app su tecnología, transporte de tokens y pantallas. No asumir React Native/Flutter/Kotlin.
- [ ] Mantener PR en borrador y `main` sin cambios hasta validación y autorización de integración.

**Lectura implementada en M2.1:** [M2.1-MOBILE-CONFIRMATION.md](M2.1-MOBILE-CONFIRMATION.md) incorpora `confirmation_readiness` para distinguir preparación B2 del requisito web local. `mobile_execution_available` conserva su significado anterior de navegación. La brecha de selección sintética desde móvil sigue fuera de alcance: no se añade ninguna escritura de pago ni se expone la fixture.
