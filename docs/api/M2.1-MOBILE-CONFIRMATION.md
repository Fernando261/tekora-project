# M2.1 — Preparación para confirmar una reserva

Lectura aditiva en `GET /api/v1/reservations/{reservation}/checkout-context` y `GET /api/v1/inquiries/{inquiry}/journey`. Mismos Bearer Sanctum, `MobileClient`, propiedad como cliente y límites existentes. No hay rutas nuevas ni comandos de pago. No se ha implementado ni probado una app nativa.

## Contrato y compatibilidad

Ambos recursos añaden `data.confirmation_readiness`. En journey corresponde a su reserva actual; es `null` sin reserva y en la proyección web del prestador. No representa nuevas capacidades de prestador móvil.

```json
{
  "state": "ready",
  "can_offer_mobile_confirmation": true,
  "advisory_only": true,
  "reservation_id": 17,
  "reservation_version": 1,
  "synthetic_web_requirement": "not_applicable",
  "blocking_reasons": [],
  "observed_at": "2030-01-01T12:00:00.000000Z"
}
```

Objeto de ejemplo, no respuesta completa. `observed_at` coincide con `data.server_now`. La versión es la de la **reserva**, no `hold.version`. El contador conserva los campos existentes: `data.hold` en checkout-context o `data.reservation.hold` en journey, con vencimiento UTC y segundos restantes. Son 900 segundos desde la aceptación del prestador; leer nunca renueva el plazo.

`can_offer_mobile_confirmation` solo es true con `state=ready`. Permite ofrecer la acción de confirmación **B2**, no iniciar un pago ni asegurar que una escritura posterior será admitida. `future_payment.enabled`, `future_payment.can_start` y `payments.enabled` siguen siendo false. No enviar campos de readiness en comandos: las allowlists existentes los rechazan.

`next_action.mobile_execution_available` conserva su semántica anterior de navegación. Puede seguir siendo true junto a `web_checkout_required`; un cliente M2.1 debe consultar el nuevo objeto para ofrecer la confirmación. No se elimina ni se redefine ese booleano. Los campos anteriores, rutas y cuerpos de escritura permanecen intactos.

La propiedad es opcional en OpenAPI para interoperar con servidores anteriores. Si falta, es null o hay error, no inferir `ready`. Consumidores JSON habituales pueden ignorar la propiedad nueva; validadores estrictos contra el esquema antiguo (`additionalProperties=false`) deben actualizar su esquema. No se garantiza compatibilidad con un parser que rechace campos desconocidos. Las pruebas preservan por fingerprint todas las propiedades y restricciones anteriores y validan separadamente la única adición autorizada; no se sustituyen los fixtures históricos.

## Estados y presentación

| `state` | Acción móvil | Interfaz sugerida |
| --- | --- | --- |
| `awaiting_provider` | No | Esperar aceptación del horario por el prestador web |
| `ready` | Sí, orientativa | Ofrecer confirmar B2 con versión actual e idempotencia |
| `web_checkout_required` | No | Explicar que esta fixture requiere completar la selección ficticia por web |
| `hold_expired` | No | Plazo terminado; refrescar y preparar otra propuesta si procede |
| `hold_released` | No | Horario liberado; conservar historial |
| `already_confirmed` | No nueva confirmación | Mostrar contratación confirmada por el servidor |
| `cancelled` / `rejected` / `completed` | No | Mostrar el estado final y su historial |
| `blocked` | No | Mostrar bloqueo operativo; refrescar según las razones |
| `not_applicable` | No | Reserva legacy: no tiene comando de commit comercial |
| `unknown` | No | Reloj observado incierto; no mostrar una confirmación disponible |

`blocking_reasons` reutiliza los bloqueos comerciales existentes: `commercial_quote_required`, `quote_not_accepted`, `reservation_not_pending`, `inquiry_not_accepted`, `hold_not_started`, `hold_not_active`, `service_already_started`, `participants_unavailable`. M2.1 añade `synthetic_web_checkout_required` y `server_clock_uncertain`. Son códigos, no mensajes a interpretar como instrucciones. Los estados terminales tienen prioridad sobre los bloqueos genéricos. Un error de almacenamiento no se convierte en una lista vacía de bloqueos.

## Regla sintética local y fuente de verdad

El modelo reutiliza los bloqueos de `CheckoutContext`; no replica un workflow ni ejecuta `decide()` para sondear permisos. Solo cuando el hold ya es comercialmente elegible evalúa el límite privado existente `LocalIntegratedCheckoutController::permitsSyntheticRequest()` y el **mismo** `LocalCheckoutAttemptStore::permitsCommit()` usado por el comando. No se cambia `ReservationWorkflow`.

`synthetic_web_requirement` significa:

- `not_applicable`: fuera del límite privado B3.2, o no hay un hold por lo demás confirmable. No significa que el backend haya validado un pago real.
- `required`: en esa fixture, falta una selección sintética que satisfaga el predicado vigente. Incluye ausencia, rechazo, error temporal o vínculo inválido; no revela método, instrumento, referencia ni diagnóstico privado.
- `satisfied`: el predicado sintético vigente ya se satisface. Tarjeta de prueba aprobada y efectivo pendiente/recibido permiten B2 conforme a B3.2. Elegir efectivo no acredita su recepción.

La regla depende del entorno, conexión SQLite desechable marcada y origen loopback del request, igual que la escritura existente. No exponer la fixture mediante LAN, Internet, proxy o túnel. No trasladar una lectura entre entornos/orígenes ni confiar en ella como autorización.

Journey obtiene el objeto del mismo `CheckoutContext`, dentro de su transacción de lectura y usando el mismo instante observado. No se escribe el reloj ni se reconcilian expiraciones desde GET. El bookkeeping normal de Sanctum (`last_used_at`) no es estado comercial. Lecturas separadas pueden observar cambios legítimos entre peticiones.

Si una reserva por lo demás preparada observa que el reloj real retrocede respecto al high-water B2, la proyección comercial anterior conserva su reloj observado, pero readiness es `unknown`, false y `server_clock_uncertain`; la escritura mantiene su rechazo 503. Si faltan almacenamiento, reloj o vínculos comprobables, se devuelve 503 sin `data`, nunca una confirmación disponible.

## Comandos, refresco y errores

1. Obtener reserva/contexto después de aceptar el prestador. Mantener `reservation_id`, versión y vencimiento.
2. Solo ofrecer confirmar con un objeto vigente `ready`. Enviar al PATCH existente `{"version":1,"idempotency_key":"UUID-estable-de-la-intencion"}`.
3. Refrescar al volver a primer plano, cambiar el horario/acuerdo, recibir un evento relevante o alcanzar el vencimiento. El contador local es orientativo; el servidor manda.
4. Ante pérdida de respuesta, consultar la reserva y reintentar la misma intención con la misma clave y versión original. Un replay confirmado sigue pudiendo ser válido aunque readiness ya diga `already_confirmed`; no generar claves nuevas para ocultar incertidumbre.
5. **409:** estado, versión o requisito cambiaron; refrescar, no afirmar éxito ni extender la retención. **422:** corregir datos conforme al contrato existente; no añadir indicadores de pago. **503:** resultado no comprobable; no tratarlo como cero bloqueos, recepción de efectivo ni confirmación. **401/403/404:** respetar autenticación y privacidad; no enumerar recursos ajenos. **429:** respetar el límite y refrescar después.

Sin migraciones, cambios de comisión (15 % ya incluida), pasarelas, instrumentos reales, pagos, recibos bancarios o nuevas escrituras financieras. La futura app y su entorno HTTPS separado continúan pendientes. Windows debe repetir la validación en copia aislada, con `.env.testing` vacío temporal y solo SQLite sintética conforme a `docs/testing/WINDOWS-ISOLATED.md`.
