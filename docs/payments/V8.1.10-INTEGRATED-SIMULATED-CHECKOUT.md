# V8.1.10 · Checkout integrado de prueba

Web y API escriben el resultado de prueba en la misma base MySQL que contiene la reserva. `TEKORA_CHECKOUT_PROCESSOR=simulated` habilita el procesador determinista. El único instrumento de tarjeta admitido es el identificador ficticio `tekora-test-card`. El formulario conserva la presentación B3.2, con datos visuales fijos y sin enviar números de tarjeta, CVV ni fechas de tarjeta. La operación deriva los participantes y el importe de la reserva y su cotización aceptada. MXN 500,00 se registra como 50.000 centavos, con 7.500 de comisión incluida y 42.500 de importe del prestador.

| Resultado | Qué permite |
| --- | --- |
| `test_approved` | Confirmación explícita por el cliente durante la retención |
| `declined`, `temporary_failure` | Reintento con otra clave, dentro del plazo |
| `awaiting_cash` | Confirmación explícita durante la retención y registro posterior por el prestador propietario si corresponde |
| `cash_received` | Consulta del resultado persistido, con la primera fecha de recepción |

La selección escribe un intento, nunca una transición de reserva. Se conserva el historial de intentos y cada reserva admite una sola selección válida. La clave UUID queda asociada al cliente, método y reserva. Repetir la misma operación devuelve la referencia persistida, incluso cuando venció la retención. Reutilizar la clave en otra operación da 409. Una selección exitosa cierra la posibilidad de registrar otra selección. El registro de recepción actualiza exclusivamente el estado y la fecha de recepción, y es idempotente.

El comando comparte el admisor de escritura B2. Después de adquirir el mutex de reservas se vuelve a leer la reserva, el actor, la cotización, la aceptación, los participantes y la retención. El reloj se consulta después de adquirir los bloqueos necesarios y el trigger comprueba el plazo de nuevo. La ventana dura 900 segundos desde la aceptación del prestador y el checkout no extiende el plazo. Las ediciones posteriores del precio o la disponibilidad siguen la política B2 de congelación; la vigencia de la cotización limita la primera aceptación. Las lecturas de seguimiento son informativas. El `PATCH /commit` valida otra vez el estado vigente y el trigger de reservas comprueba la selección válida al confirmar.

El marcador `service_reservations.checkout_required` se fija al crear una propuesta comercial con el procesador habilitado. Permanece vigente si cambia la configuración, conserva el historial y bloquea la confirmación sin selección. Las reservas anteriores al cambio conservan el marcador en cero, incluidas las pendientes y sus retenciones. Las propuestas sin cotización mantienen el contrato histórico. El modo por defecto `disabled` conserva el flujo histórico para nuevas propuestas cuando se usa deliberadamente sin habilitar el procesador. Un valor desconocido bloquea nuevas propuestas comerciales. Las interfaces `/demo/checkout`, `/demo-checkout` de API y las páginas B3.2 originales conservan sus restricciones.

## Web y móvil

1. Tras la aceptación del prestador, el detalle de solicitud y de reserva muestra la acción de checkout al cliente. La página oficial está en `/cuenta/reservas/{id}/pago-de-prueba`.
2. En móvil, consultar el contexto y el seguimiento. Si `simulated_checkout.required` está presente, usar `GET /api/v1/reservations/{id}/checkout` para recuperar la selección después de recargar. Si el objeto está ausente, conservar el flujo legado y su compatibilidad con el laboratorio local.
3. Usar `POST` sobre esa ruta con `method`, `idempotency_key` y, solo para tarjeta, `instrument: "tekora-test-card"`. Persistir la clave por acción hasta obtener una respuesta definitiva. Ante desconexión, consultar el estado y reintentar la misma acción con la misma clave. Un rechazo o fallo temporal puede iniciar otro intento con una clave nueva si `can_choose` sigue vigente.
4. Confirmar solo tras acción explícita del cliente, usando `PATCH /api/v1/reservations/{id}/commit`, su versión y una clave UUID propia de la confirmación. Refrescar al recibir 409. `requires_verified_payment` y `future_payment.enabled` permanecen en false; `synthetic_only` siempre es true para los intentos.
5. El prestador ve el resultado y registra efectivo desde el detalle web. El cliente recupera la recepción desde la API existente en esta entrega. Tras prestación y finalización explícita, las reglas de reseñas siguen vigentes.

Los ejemplos reproducibles están en [V8.1.10-integrated-checkout.http](../api/examples/V8.1.10-integrated-checkout.http) y el contrato en [OpenAPI](../api/openapi.json). La aplicación móvil requiere implementar o actualizar su pantalla para consumir este contrato. El comprobante de Tekora es exclusivamente interno y no acredita recepción bancaria, liquidación ni pago fiscal.
