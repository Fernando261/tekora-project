# B3.1-D — Checkout de demostración

Solo local/testing, en la rama del incremento. No es la implementación de la pasarela B3.1. Ningún resultado demo es paid/captured real; no hay cobros, saldos, liquidaciones o comprobantes de banco. El encabezado de éxito de presentación dice «¡Pago realizado con éxito!» y permanece acompañado del comprobante interno DEMO y la aclaración de que no hubo cobro externo.

## Preparación reproducible

Usar una copia nueva del commit entregado, con PHP CLI, Composer y npm. No copiar .env, SQLite o credenciales de otra instalación. Instalar con composer install --no-scripts --prefer-dist --no-interaction, npm ci y npm run build. No ejecutar migraciones para esta demo. Los dos avisos de fuentes locales del build son previos; comprobar que los assets locales carguen.

En PowerShell, desde ese checkout independiente (sin .env ni bootstrap/cache/config.php), ejecutar el siguiente bloque. Todas las variables se limitan al proceso de esta terminal y se restauran al detener el servidor. No modifica Laragon, MySQL, Docker ni variables de usuario/sistema.

```powershell
$ErrorActionPreference = 'Stop'
if ((Test-Path .env) -or (Test-Path bootstrap/cache/config.php)) { throw 'Usar una copia aislada sin entorno ni cache previa' }
$names = @('APP_ENV','APP_KEY','APP_DEBUG','DB_CONNECTION','DB_DATABASE','DB_URL','CACHE_STORE','SESSION_DRIVER','APP_CONFIG_CACHE','TEKORA_CHECKOUT_DEMO_ROOT')
$previous = @{}
foreach ($name in $names) { $previous[$name] = [Environment]::GetEnvironmentVariable($name, 'Process') }
try {
    $bytes = New-Object byte[] 32
    $rng = [Security.Cryptography.RandomNumberGenerator]::Create()
    try { $rng.GetBytes($bytes) } finally { $rng.Dispose() }
    $env:APP_KEY = 'base64:' + [Convert]::ToBase64String($bytes)
    $env:APP_ENV = 'local'; $env:APP_DEBUG = 'false'
    $env:DB_CONNECTION = 'sqlite'; $env:DB_DATABASE = ':memory:'; $env:DB_URL = ''
    $env:CACHE_STORE = 'array'; $env:SESSION_DRIVER = 'array'
    $id = [Guid]::NewGuid().ToString('N')
    $env:APP_CONFIG_CACHE = Join-Path $env:TEMP "tekora-demo-no-config-$id.php"
    $env:TEKORA_CHECKOUT_DEMO_ROOT = Join-Path $env:TEMP "tekora-checkout-demo-$id"
    php artisan demo:checkout-prepare $env:TEKORA_CHECKOUT_DEMO_ROOT --url=http://127.0.0.1:8097
    if ($LASTEXITCODE -ne 0) { throw 'Preparacion fallida: no iniciar la demo' }
    php artisan serve --host=127.0.0.1 --port=8097
} finally {
    foreach ($name in $names) { [Environment]::SetEnvironmentVariable($name, $previous[$name], 'Process') }
}
```

Abrir http://127.0.0.1:8097/demo/checkout. El comando muestra un enlace privado para el presentador: abrirlo en otro perfil/ventana independiente para la vista del prestador. Ese acceso es una capacidad sintética, no un login o permiso comercial de un usuario real. No compartirlo, grabarlo ni subirlo a artefactos. La redirección limpia su URL; cookies HttpOnly/SameSite=Strict y Referrer-Policy=no-referrer. Windows debe mantener la carpeta privada para la cuenta local mediante sus ACL. Linux exige 0700/0600. No se eliminan directorios existentes; la preparación rechaza reutilizar un directorio. Tras detener el servidor, conservar o descartar únicamente esa carpeta sintética propia, nunca bases de la aplicación.

En Linux son equivalentes las mismas variables de proceso y los comandos artisan anteriores, con una ruta absoluta canónica nueva (por ejemplo una carpeta con UUID bajo /tmp). No hace falta preparar SQLite: la demo no consulta ninguna base, ni siquiera para sesiones.

## Guion de presentación

1. Mostrar el aviso de entorno de pruebas, resumen, cotización ficticia aceptada, total MXN y 15 % incluido. El temporizador de 900 segundos es una fixture independiente de cualquier reserva real.
2. Elegir Tarjeta y un instrumento predefinido. Enfocar Código demo para ver el reverso y cambiar de campo para regresar. Confirmar pago: salida del formulario, centrado, procesamiento y transformación menta. Mostrar importe, método y referencia TK-DEMO, que no es bancaria.
3. Recargar: se consulta el resultado persistido; no se crea otro intento. Volver al detalle desplaza el foco al resumen.
4. Preparar otro ejemplo, elegir Efectivo y confirmar. Queda pendiente, sin comprobante ni éxito. En la vista privada del prestador, buscar el mismo código de ejemplo y pulsar «Representar recepción de efectivo». El cliente consulta y muestra la confirmación del servidor.
5. Crear ejemplos nuevos para rechazo y error temporal; reintentar el error conserva la misma intención y no duplica el comprobante. Una avería de transporte muestra resultado desconocido, nunca éxito; consultar/reintentar recupera desde el servidor.

## Frontera técnica y seguridad

La antigua maqueta solo JavaScript pasa a consultar endpoints privados bajo /demo/checkout. Conserva Anime.js, giro 3D, curvas/tiempos principales y estilos aislados. Nunca hay campos libres para PAN/CVV: solo tokens ficticios debit/credit y selectores de presentación. Los campos bancarios, importes, IDs comerciales, estados o actores enviados por el cliente se rechazan. CSP permite conexión únicamente al mismo origen; sigue bloqueando formularios, frames y recursos externos. Se usan cookies propias de demo; StartSession, ShareErrorsFromSession y CSRF de la sesión comercial se excluyen únicamente en estas rutas. La demo valida su propio token CSRF vinculado a la capacidad y Origin, también bajo testing.

CheckoutStore usa una carpeta privada nueva, marcador de tipo, archivos JSON y flock exclusivo por contexto; no es un adaptador PricingStore ni una tabla de pagos. Cliente y operador tienen capacidades independientes. El cliente no recibe el secreto del operador ni puede registrar efectivo por enviar actor=provider_demo. El archivo guarda hashes de capacidades; los comprobantes nunca son recibos de pasarela. JSON corrupto, fallo de escritura o entorno no preparado: error explícito sin resultado exitoso. No se certifica recuperación frente a cortes físicos de energía; es almacenamiento descartable de presentación.

Se reutilizan CommercialAmount y los value objects/recursos de cotización B3.0 para construir una fixture aceptada, sin emitir/aceptar cotizaciones de la base comercial. Sus IDs son exclusivamente sintéticos dentro del contexto isolated_demo y no se buscan en la aplicación. No se llama a CheckoutContext sobre reservas existentes ni se modifican workflows, retenciones o decisiones comerciales pendientes.

Estados internos: demo_completed, demo_declined, demo_temporary_error y demo_awaiting_cash; demo_expired es una proyección de la retención vencida. Repetir idempotency_key con igual contenido conserva el intento; cambiar contenido produce conflicto. Una intención completada, pendiente de efectivo o temporal impide otra en el mismo contexto. La recuperación temporal usa una acción explícita y conserva ID y referencia. El botón «Preparar otro ejemplo» crea una fixture independiente: no renueva el contexto anterior ni una reserva real.

El hold sintético usa BookingClock.HOLD_MICROSECONDS: exactamente 900.000.000 microsegundos. Se conserva el máximo tiempo observado incluso en admisiones fallidas; polling, recargas, reintentos, recepción y retrocesos del reloj no amplían su vencimiento. Al vencer no se admite otro intento o recepción; resultados ya completados conservan su historia. Las retenciones B2 y su confirmación vigente permanecen intactas.

## Integración posterior y límites

La app móvil real debe consumir el contexto comercial autenticado de B3.0; no estos endpoints, cookies o credenciales demo ni el HTML. Una implementación financiera posterior requiere autorización específica, persistencia durable de intentos/idempotencia, tokenización/3DS mediante SDK externo, webhooks verificados, reconciliación de estados inciertos, compensación al vencer el hold y política central de confirmación sin bypass, conforme a B3.1. No convertir un evento visual, un comprobante demo o demo_completed en evidencia financiera. Efectivo real requiere confirmación legítima del prestador autorizado y una política aprobada; elegir el método nunca acredita recepción. Nada de eso está activado aquí.

Comisión 15 % incluida, costos de procesamiento futuros absorbidos por Tekora y liquidación posterior al servicio +48 horas siguen siendo condiciones del diseño, sin movimientos de dinero. No se altera B3.1 ni se modifica el contrato /api/v1. Validación nativa de Windows/Laragon y app móvil: pendiente para este incremento. Los resultados reales, capturas y grabaciones se entregan fuera del repositorio.
