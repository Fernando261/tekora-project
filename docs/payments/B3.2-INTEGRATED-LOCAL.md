## Qué está implementado

Desde la solicitud y retención B2 activa del cliente, el acceso `Elegir método de pago` abre `/cuenta/reservas/{reservation}/checkout` dentro de la interfaz estándar Tekora. La pantalla obtiene servicio, prestador, snapshot de cotización, importe total y vigencia del `CheckoutContext` comercial real de la **base de pruebas**. No usa los 1,000 MXN constantes del antiguo `/demo/checkout`.

Tarjetas de prueba seleccionables: `4242424242424242` aprobada, `4000000000000002` rechazada, `4000000000000119` error temporal; vencimiento único 12/30, CVV de prueba 123. También hay efectivo pendiente. El servidor restringe las entradas a estos valores, guarda únicamente método, estado, monto acordado, participantes, referencia y clave idempotente; **no guarda PAN ni CVV**, no contacta bancos, no genera cobros, recibos reales, saldos ni webhooks. El checkout identifica discretamente el entorno local de pruebas para no confundir una aprobación ficticia con un cobro.

Cuando el cliente selecciona efectivo, el prestador puede abrir `/cuenta/reservas/{reservation}/checkout/efectivo` desde su seguimiento y registrar la recepción **sintética** en otro navegador/perfil. El cliente puede recargar y ver ese estado. Solo el prestador propietario y con permiso vigente puede registrar efectivo. La retención no se renueva. La selección sintética por sí sola no cambia `service_reservations` ni confirma la reserva: la confirmación B2 sigue siendo una acción explícita, ahora supeditada a un método ficticio aceptable **solo en esta SQLite temporal**.

La tabla `synthetic_checkout_attempts` se crea **únicamente** durante el generador de SQLite desechable de `tools/tekora-b32-fixture.php`; **no está en migraciones**. No hay escritura de estados financieros en bases comerciales. El checkout original B3.1-D sigue intacto como herramienta separada; no es la ruta que debe usarse para esta presentación.

## Preparar la versión real de Tekora para Windows 11

1. Descarga una **copia nueva** de la rama en GitHub fuera de `C:\laragon`, fuera del proyecto de desarrollo y sin copiar ningún `.env`, SQLite, archivos de sesión, certificados, llaves o credenciales.
2. En esa carpeta aislada: `composer install --no-scripts --prefer-dist --no-interaction`, `npm ci`, `npm run build`. No ejecutes migraciones manualmente ni conectes Docker.
3. Abre PowerShell en esa copia y ejecuta `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tools\tekora-b32-test-windows.ps1"`. Si falla, **no anuncies PASS**: conserva la salida de error y el reporte en `%TEMP%`.
4. En otra terminal de PowerShell (si las pruebas pasaron): `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tools\tekora-b32-launch-windows.ps1"`. El script primero migra SQLite `:memory:`, crea cuentas mediante fixtures existentes, exporta una **base nueva** con `VACUUM INTO` al directorio temporal `tekora-b32-<id>`, añade marcador privado y arranca Laravel solo en `127.0.0.1:8097`. Genera clave de aplicación solo en el proceso y no utiliza .env existentes.
5. Copia las credenciales temporales que imprime el lanzador. Abre `http://127.0.0.1:8097/login` en dos perfiles distintos del navegador (cliente y prestador). Hay una solicitud pendiente para la primera parte del recorrido y otra con cotización/horario retenido para entrar directamente a pago. Tras 900 segundos desde la aceptación, la retención caduca: genera una SQLite **nueva**; nunca manipules manualmente el reloj, renueves esa reserva ni reutilices un directorio existente.

No se ha sustituido el checkout anterior ni su JavaScript. El integrado conserva sus propios formularios POST con validación en servidor y únicamente datos ficticios; no se implementan cobros reales. Se corrigió la jerarquía de estados: después de una aprobación de prueba con retención activa se indica volver a confirmar la reserva, sin mostrar falsamente que la retención ha vencido.

**Estado visual:** el usuario confirmó la apariencia correcta del checkout integrado después de la corrección. La verificación automatizada final del HEAD más reciente sigue necesitando un log de Windows adjunto al PR.

## Revisión de checkout: retención, confirmación y presentación (19/11/2026)

La cabecera interna `co-shell-header` tenía fondo blanco y comportamiento fijo porque `public/css/tekora/account-base.css` aplica estilos a `header` globalmente. `checkout-integrated.css` los neutraliza **solo** dentro de la cabecera Blue Obsidian de esta página. Al recibir un resultado tras POST/303, el servidor marca esa navegación una sola vez y la vista sitúa el panel/recibo dentro del área visible, también en móvil.

**Regla exclusiva de B3.2 sintético:** para una reserva cotizada con retención vigente, el cliente debe registrar una opción antes de confirmar definitivamente. La acción `commit` se bloquea en `ReservationWorkflow`, dentro de la transacción de escritura, si la SQLite local marcada no tiene un resultado válido para el mismo cliente, prestador, cotización e importe. Una tarjeta aprobada ficticiamente permite seguir; un rechazo o error temporal **no**. El efectivo seleccionado queda pendiente de recepción, pero permite confirmar el horario; el prestador puede registrar la recepción de prueba después, con sus permisos. Los controles visuales ocultan el botón prematuro, pero **la seguridad no depende del navegador**.

Esta nueva exigencia solo entra en vigor cuando `LocalIntegratedCheckoutController::permitsSyntheticRequest(request())` reconoce una SQLite temporal marcada y el origen local de demostración. La política B2 normal, las bases existentes, `main`, y todas las conexiones bancarias siguen sin modificarse. Una selección ficticia no acredita dinero; la confirmación sigue siendo explícita.

**Estado:** revisión visual de usuario positiva; última evidencia automática incompleta por una regresión de expectativa ya corregida. No anunciar PASS total del HEAD hasta adjuntar el resultado completo del verificador.

## API móvil y límites

La API existente `GET /api/v1/reservations/{reservation}/checkout-context` ofrece **paridad de lectura** para una aplicación móvil; por contrato sus pagos están deshabilitados. **No se ha implementado la API móvil que escriba resultados de pago de prueba**; es un pendiente de paridad de escritura. No dirigir la app nativa a las rutas web de sesión ni a `/demo/checkout`. Tampoco está concluida la prueba con una app móvil real.

No usar esta rama en producción, no alojar la fixture en Internet, no abrir puertos distintos del loopback local, ni integrar pasarela real sin una etapa posterior expresamente autorizada.
