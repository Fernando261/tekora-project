# Tekora W5.1 · Integridad de fotografías

Base aprobada: `cc27543de2f7c24aa405c218b580cc3b52ed2532`. Rama: `codex/web-w51-photo-integrity`. PR nuevo en borrador, independiente de W5; sin fusión ni despliegue. Los SHA completos de implementación y entrega se registran al publicar.

La corrección se limita a `ProfileController::updatePhoto` y un archivo nuevo de pruebas. No cambia el diseño aprobado, las vistas, CSS/JS, rutas, autorización, guards, modelos, migraciones, API, dependencias, configuración ni pruebas anteriores. [Guía Windows/Laragon](W51-LARAGON.md).

## Defecto y evidencia antes/después

El controlador anterior eliminaba la foto primero, generaba el nombre mediante `time()`, ignoraba el resultado de `put()` y guardaba la referencia aunque no existiera el archivo. La [evidencia W5](../w5/evidence/photo-integrity.json) y su [inventario](../w5/W5-MINDBLOOM-INVENTORY.md) documentan el defecto. El controlador de la base W5.1 coincide exactamente con ese código.

La prueba `test_a_false_write_preserves_the_old_reference_and_file_and_reports_photo_error` se ejecutó primero contra el controlador aprobado: [fallo esperado](evidence/before-false-write.txt), con referencia modificada pese a devolver `false`. La misma prueba pasa con la corrección y verifica SQL, existencia y bytes de los archivos, errores de `photo` y ausencia de éxito.

El [reproductor CLI](evidence/reproduce-false-write.php) usa SQLite `:memory:`, fotos falsas y un proxy que devuelve `false`, sin cambiar el archivo de producción. En modo `before` carga la [copia exacta del controlador aprobado](evidence/approved-controller.php.txt), comprobada por SHA-256; en `after` carga la implementación actual. El propio reproductor impide su uso como endpoint web y usa una ruta `.env` inexistente.

```powershell
php -d memory_limit=256M docs/web/w51/evidence/reproduce-false-write.php before
php -d memory_limit=256M docs/web/w51/evidence/reproduce-false-write.php after
```

Ambos diagnósticos deben terminar con código 0 porque comprueban el comportamiento esperado de cada versión. La ejecución PHPUnit previa termina con código 1, que es el fallo de regresión demostrado, no una validación aprobada.

## Algoritmo corregido

1. Conserva POST `/perfil/foto`, guard `web`, CSRF, `photo`, multipart, reglas `image`/JPG/JPEG/PNG/WebP/2048 KB, disco `public`, `profile_photo_path` y redirección de regreso. Retira un mensaje de éxito anterior al iniciar el intento y al fallar.
2. Genera `avatars/avatar_<id>_<128 bits aleatorios>.<extensión>`. Respeta las extensiones válidas; un nombre suministrado con otra extensión usa la extensión MIME validada. No usa tiempo ni el nombre original para formar la ruta. Si el destino ya existe o resuelve fuera de la raíz local autorizada, falla antes de escribir o intentar compensarlo.
3. Lee los bytes del upload validado (máximo 2 MiB) y usa `FilesystemAdapter::put` con una cadena. No deja un stream abierto a cargo del controlador. Exige resultado `true`, existencia, tamaño exacto y SHA-256 de lectura idéntico. Esto rechaza `false`, resultado vacío, excepciones, escrituras parciales, contenido corrupto del mismo tamaño y éxitos sin archivo.
4. Abre una transacción propia. Rechaza un contexto ya transaccional: un savepoint no confirma el commit exterior. Lee una instancia fresca del usuario desde el PDO de escritura con `lockForUpdate`, conserva su referencia real y guarda únicamente la nueva referencia. Comprueba el resultado de `save()` y vuelve a leer el valor SQL dentro de la transacción para detectar updates ignorados.
5. Confirma la transacción, comprueba que no quede abierta y vuelve a confirmar la referencia en el PDO de escritura. Si otra petición ya ganó antes de esa confirmación, no anuncia éxito de una referencia que no puede confirmar. La compensación nunca elimina la foto ganadora.
6. Ante fallo de escritura/persistencia intenta resolver el rollback propio y limpia solo el destino nuevo de esta operación cuando no esté referenciado. Ante estado SQL ambiguo, transacción aún abierta, referencias existentes o fallo de lectura, conserva el archivo antes que borrar una posible referencia válida. Devuelve un error genérico asociado a `photo`, sin SQL, rutas ni stack traces.
7. Solo tras confirmar SQL intenta retirar la foto anterior. Un fallo de borrado no revierte la referencia nueva ni se transforma en un error de subida. Actualiza únicamente la referencia de foto en el usuario cacheado de esta petición a partir de SQL; nunca guarda sus otros atributos potencialmente desactualizados.
8. Si la operación se confirma devuelve exactamente `Foto de perfil actualizada.`. Los fallos controlados devuelven `No se pudo actualizar la foto. Inténtalo de nuevo.`; los errores originales de validación conservan sus reglas y mensajes.

La escritura/verificación del archivo y toda limpieza ocurren fuera de la transacción SQL. No hay locks globales, espera artificial ni reintentos largos introducidos por W5.1.

## Fotos anteriores y otros medios

La referencia anterior procede del usuario leído bajo lock, nunca del POST ni del objeto autenticado obsoleto. El borrado admite únicamente archivos de imagen con nombre plano en `avatars/` y en el namespace legado `historical/`, conservado por el contrato de las pruebas W5. No hay excepciones por nombre de fixture ni código distinto para testing. Una ruta con dueño codificado `avatar_<id>_...` debe corresponder al usuario actual.

Se rechazan URLs, rutas absolutas, `..`, subdirectorios arbitrarios y rutas de otros módulos. En disco local se resuelve la raíz y el ancestro existente para evitar salir de ella mediante alias/symlinks. Antes de eliminar se consultan referencias actuales de todos los usuarios y los campos de medios conocidos de posts, comentarios y emociones, incluyendo claves literales dentro de URLs/dominios históricos con query o fragmento y comparación conservadora de mayúsculas. El LIKE parametrizado escapa el guion bajo literal; las coincidencias conservadoras pueden retener archivos adicionales, nunca autorizan un borrado adicional. No se leen los bytes del archivo antiguo para decidir su dueño.

Una foto compartida o todavía referenciada se conserva. Una referencia no administrada se deja pendiente, aunque ya no sea la foto vigente. La pertenencia de una foto heredada sin ID depende de la referencia SQL confirmada y de la ausencia de referencias conocidas: no se inventa un registro histórico de propietarios. Metadatos corruptos o referencias externas desconocidas requieren revisión autorizada; no se afirma poder reconstruir su procedencia.

Los avisos solo contienen un texto fijo y una fase técnica (`write`, `persistence`, `previous-file-cleanup`, `new-file-compensation`, etc.). No incluyen usuario, correo, rutas, contenido ni mensajes de excepción. Un fallo del logger tampoco dispara borrados ni revierte un commit. No se añade un barrido, job ni comando de limpieza global.

## Concurrencia y límites

- Dos subidas en el mismo segundo usan nombres diferentes con 128 bits CSPRNG. Se rechaza un destino existente. No se afirma una creación atómica `O_EXCL`: la comprobación de existencia no elimina por sí sola una carrera; los identificadores independientes hacen despreciable la colisión accidental.
- Los atributos obsoletos no se guardan. En motores con soporte, el lock afecta la fila de esa cuenta durante las operaciones SQL, sin mantenerlo durante I/O de almacenamiento.
- Todos los escritores W5.1 publican una clave nueva y nunca vuelven a asignar una clave retirada. El borrado usa la referencia sustituida bajo lock y consulta el PDO de escritura antes de eliminarla. Así una limpieza retrasada no elige la foto ganadora de otra petición.
- Se prueban intercalados deterministas antes de publicar, tras el commit y durante la limpieza, con SQL y archivos falsos reales. No son conexiones paralelas ni una prueba de carga. SQLite `:memory:` no implementa el mismo lock de fila que MySQL/InnoDB; no se presenta la suite como demostración de concurrencia multiproceso en Windows/MySQL.
- Una segunda petición puede ganar antes de la confirmación de la primera: la primera responde con error genérico, conserva la ganadora y puede dejar una foto anterior pendiente. El mensaje no promete deshacer cambios ya confirmados por otra petición.
- Un commit puede aplicarse y perder su confirmación. Se simula ejecutando el commit PDO real y lanzando después una excepción. La referencia confirmada no se revierte ni se borra su archivo; puede mostrarse error y permanecer el anterior. Si el rollback tampoco se puede confirmar, se conservan ambos archivos para no borrar datos posiblemente referenciados.

SQL y el almacenamiento son recursos distintos: **no hay atomicidad total**. Una caída tras escribir y antes de SQL puede dejar un archivo nuevo sin referencia; tras el commit y antes de retirar el anterior puede dejar el antiguo. Un fallo de compensación también puede dejar un candidato pendiente. Se registran las fases, sin anunciar éxito de una escritura/persistencia fallida, y no se ejecuta una recolección destructiva para ocultarlo.

La verificación comprueba los bytes visibles antes de publicar, no garantiza `fsync`, supervivencia a pérdida de energía ni integridad ante un proceso externo que borre archivos, reasigne rutas viejas, altere metadatos o cambie directorios/symlinks durante la operación. Almacenamientos remotos o con lecturas eventualmente consistentes no se validaron: pueden provocar rechazo conservador y limpieza pendiente. Solo se probó disco local falso; no se tocaron proveedores ni medios reales.

## Casos de fallo

| Caso | Base aprobada | W5.1 verificado |
| --- | --- | --- |
| `put() => false` | Medido: elimina anterior, cambia referencia e informa éxito sin archivo | Error `photo`, referencia/bytes anteriores intactos, sin candidato restante |
| Excepción o escritura parcial | Análisis: la anterior ya fue eliminada; no verifica integridad | Anterior intacta; compensa solo el archivo nuevo |
| `true` con bytes corruptos/missing | Análisis: guarda referencia y puede anunciar éxito | Tamaño/hash/existencia rechazan la escritura |
| Error SQL, veto del modelo o UPDATE ignorado | Análisis: anterior eliminada, sin compensación | Rollback y limpieza del candidato; no éxito |
| Commit falla o devuelve `false` | Sin protocolo explícito de confirmación/compensación | Verifica estado PDO/SQL, conserva anterior y compensa cuando es seguro |
| Error después de commit real | Sin tratamiento explícito | Conserva referencia/archivo nuevo y anterior; error, sin revertir a ciegas |
| Borrado antiguo falla | Ignora resultado | Nueva foto válida, éxito de actualización y aviso técnico de limpieza |
| Mismo segundo / usuario obsoleto | Nombre temporal y objeto cacheado | Nombre aleatorio, instancia fresca y referencia ganadora preservada |
| Rutas manipuladas / medios compartidos | Borrado directo de la referencia | Conserva medios fuera de política o referenciados |

Solo la fila `false` se reprodujo contra el código anterior en W5.1; los demás comportamientos anteriores se describen como análisis del código, no como pruebas ejecutadas. Todos los resultados W5.1 de la tabla se verifican en el grupo nuevo.
